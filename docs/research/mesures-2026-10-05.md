## 1. Laptop — `llama-bench` (CPU only)

Intel i7-1370P (6 P-cores + 8 E-cores, 20 threads), 30 Go RAM.
Commande : `llama-bench -m <A>,<B> -p 512 -n 128 -t 6,14 -r 3`.

| Modèle | Fichier | Params | Threads | pp512 (prefill) t/s | tg128 (decode) t/s |
|---|---:|---:|---:|---:|---:|
| LFM2.5-8B-A1B UD-Q5_K_M (MoE, ~1,5B actifs) | 5,92 GiB | 8,47 B | 6 | 72,6 ± 3,6 | **34,6 ± 0,5** |
| idem | | | 14 | **98,0 ± 1,4** | 26,4 ± 0,1 |
| Spark-X2.5-4B Q4_K_M (dense) | 2,42 GiB | 4,11 B | 6 | 46,2 ± 0,6 | **14,8 ± 0,4** |
| idem | | | 14 | 52,7 ± 0,2 | 15,1 ± 0,1 |

Lectures :

- **Le MoE 8B décode 2,3× plus vite que le dense 4B**, alors que son fichier
  est 2,4× plus gros : le decode lit les poids **actifs**, pas les poids totaux.
- **Bande passante effective identique** pour les deux modèles :
  dense 2,42 GiB × 14,8 t/s ≈ **38 Go/s** ; MoE ≈ 1,5 B actifs × 6 bpw ≈ 1,1 Go
  × 34,6 t/s ≈ **39 Go/s**. Le decode CPU est borné par la mémoire, pas par
  le calcul (estimation : la part exacte des poids lus par token pour le MoE
  inclut embeddings/attention partagés).
- **Plus de threads ≠ plus vite** : passer de 6 (P-cores) à 14 threads accélère
  le prefill (+35 %) mais **ralentit** le decode du MoE (−24 %). Le decode
  est saturé en bande passante ; les E-cores ajoutent de la synchronisation.
- **Sur CPU, le prefill n'est que 2 à 4× plus rapide que le decode** (et non
  « un à deux ordres de grandeur » comme dans la table GPU/inconnue de la doc
  quantize). Conséquence agentique : un prompt de base de 15 000 tokens à
  ~100 t/s = **~2,5 min avant le premier token** sur ce laptop.

## 2. Laptop — mémoire allouée selon le contexte (logs `llama-cli -v`)

`llama-cli -m … -c <N> [-ctk q8_0 -ctv q8_0] -n 1 -p hi -st -v`, lignes
`llama_kv_cache: size = …` et `common_memory_breakdown_print`.

| Modèle | Couches avec KV | -c 4096 | -c 32768 | -c 131072 (f16) | -c 131072 (q8_0) |
|---|---|---:|---:|---:|---:|
| LFM2.5-8B-A1B (hybride : 6 couches attention GQA sur 24, le reste conv) | 6 × 8 têtes KV × 64 | 48 MiB | 384 MiB | 1 536 MiB | 816 MiB |
| Spark-X2.5-4B (9 couches globales + 27 en sliding window 512/1024 cellules) | 9 × 4 têtes KV × 256 | 144 (+108) MiB | 1 152 (+108) MiB | 4 608 (+108) MiB | 2 448 (+57) MiB |

- La formule **2 (K et V) × couches × têtes KV × dim tête × octets × tokens**
  se vérifie exactement : LFM2.5 = 12 KiB/token, Spark-X2.5 (couches
  globales) = 36 KiB/token. Par comparaison, un dense classique type
  Llama-3.1-8B (32 couches × 8 × 128) = 128 KiB/token → **16 GiB à 128k**.
- `q8_0` divise le KV cache par ~1,9.
- Le KV cache est **réservé au démarrage** pour tout `-c` (taille fixe),
  pas au fil de la conversation.
- `CPU model buffer size = 0.00 MiB` : les poids sont **mmappés**, pas copiés
  — le fichier est servi par le page cache de l'OS.
- Les couches récurrentes de LFM2.5 ont un état fixe minuscule
  (`llama_memory_recurrent: size = 0.28 MiB`), indépendant du contexte.
- Exemple de breakdown (Spark-X2.5-4B, `-c 32768`) : model 2 460 MiB +
  context 1 260 MiB + compute 108 MiB.
- Le prompt réellement envoyé au modèle après le chat template (Spark) :
  `<｜start▁of▁sentence｜><|System|>\nyou are a helpful assistant.<｜end▁of▁sentence｜><｜start▁of▁sentence｜><|User|>hi<｜end▁of▁sentence｜><｜start▁of▁sentence｜><|Bot|><think>`
  — « hi » coûte 17 tokens de prompt.

## 4. Laptop — le modèle du live 1 (`unsloth/Qwen3-0.6B-GGUF`, `Qwen3-0.6B-Q4_K_M.gguf`)

`llama-cli -m Qwen3-0.6B-Q4_K_M.gguf -n 32 -p "Bonjour, qui es-tu ?" -st -v`
(téléchargé dans le scratchpad, pas dans `models/`) :

- `file size = 372.65 MiB (5.24 BPW)` ; `n_ctx_train = 40960` → `n_ctx = 40960`
  (sans `-c`, le contexte complet du GGUF est réservé).
- `llama_kv_cache: size = 4480.00 MiB (40960 cells, 28 layers …)` :
  28 × 8 têtes KV × 128 × 2 × 2 o = 112 KiB/token.
- Breakdown : model 167 MiB (+ 204 MiB CPU_REPACK) + **context 4 480 MiB** +
  compute 66 MiB → **le KV cache pèse 12× les poids**. Avec `-c 4096` : ~448 MiB.
- Prompt rendu pour « hi » (`-c 4096 -p hi -v`) :
  `<|im_start|>user\nhi<|im_end|>\n<|im_start|>assistant\n` → `prompt_n = 9`
  (template ChatML, pas de prompt système par défaut).
